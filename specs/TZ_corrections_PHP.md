## К-1. Справочник кампаний: добавить поля `state`, `from_date`, `to_date`

**Заменяет:** §4.1 (`get_campaign_dict()`), §7.1 (пример таблицы), дополняет §9 (критерии приёмки).

### 1.1. Суть изменения

В справочник кампаний добавляются три поля, которые **уже приходят в том же самом ответе**
`GET /api/client/campaign` и сейчас отбрасываются:

| Новое поле | Ключ в API |
|---|---|
| `state` | `state` |
| `from_date` | `fromDate` |
| `to_date` | `toDate` |

**Дополнительных HTTP-запросов не требуется.** Метод, число запросов и схема авторизации
не меняются: как и раньше, это один `GET /api/client/campaign` без query-параметров,
без пагинации, весь список приходит за один ответ.

### 1.2. Итоговый состав и порядок колонок `get_campaign_dict`

Было 10 колонок, стало 13. Новые вставляются **сразу после `campaign_name`**, до блока
константных полей.

| # | Поле | Тип | Источник в API (ключ) |
|---|------|-----|-----------------------|
| 1 | `campaign_id` | string | `id` |
| 2 | `campaign_name` | string | `title` |
| 3 | `state` | string | `state` |
| 4 | `from_date` | string (`YYYY-MM-DD`) | `fromDate` |
| 5 | `to_date` | string (`YYYY-MM-DD`) | `toDate` |
| 6 | `account_id` | integer | **константа** (пример `1`, задаётся на стороне клиента) |
| 7 | `source_type_id` | integer | **константа** (пример `9`) |
| 8 | `product_id` | integer | **константа** (пример `1`) |
| 9 | `product_name` | string | **константа** (пример `"prod_test"`) |
| 10 | `camp_type` | string | **константа** (пример `"camp_test"`) |
| 11 | `camp_category` | string | **константа** (пример `"cat_test"`) |
| 12 | `id_key_camp` | string | **вычисляется**: `account_id + "_" + campaign_id` |
| 13 | `owner_id` | integer | **константа** (пример `1`) |

Правила по константным и вычисляемому полям — без изменений по базовому ТЗ §4.1.

### 1.3. Семантика новых полей

#### `state` — состояние кампании

Строка-перечисление. Значения, **фактически наблюдавшиеся** на живом аккаунте
(замер 17.09.2026, 119 кампаний):

| Значение | Встретилось |
|---|---:|
| `CAMPAIGN_STATE_FINISHED` | 97 |
| `CAMPAIGN_STATE_ARCHIVED` | 12 |
| `CAMPAIGN_STATE_RUNNING` | 7 |
| `CAMPAIGN_STATE_INACTIVE` | 3 |

> Это перечень **наблюдавшихся**, а не полный перечень возможных значений: замер сделан
> на одном аккаунте в один момент времени. В официальной документации полный список
> значений не подтверждён.
>
> **Требование:** значение класть в выход **как есть, строкой**. Запрещено отбрасывать,
> заменять на `null` или падать на значении, которого нет в таблице выше. Незнакомое
> состояние — это новое состояние Ozon, а не ошибка данных. Если нужна классификация
> (активна/неактивна) — делать её отдельным вычисляемым полем, не подменяя `state`.

#### `from_date`, `to_date` — период проведения кампании

Плановые даты начала и окончания пролёта кампании.

- **Формат:** `YYYY-MM-DD`, только дата. Времени и часового пояса в значении нет
  (проверено: 119 из 119 значений разобрались как `YYYY-MM-DD`, ни одного с временем).
- **Тип на выходе:** строка. Не приводить к `DateTime` и не переформатировать —
  выход должен совпадать со значением API байт в байт.
- **Порядок границ:** `from_date <= to_date` всегда (замер: 116 случаев «строго меньше»,
  3 случая «равны», ни одного «больше»).
- **Граница `to_date`, по имеющимся данным, включительная.** Основание: есть кампании,
  у которых `from_date == to_date` — при исключительной границе это кампании нулевой
  длительности. Косвенно то же показывает бюджет: там, где общий бюджет ровно делится на
  дневной (22 кампании из 119), отношение совпало с числом дней включительно в 21 случае
  и исключительно в 1.
  > **Оговорка:** это вывод из данных, а не из документации. У 97 кампаний из 119 бюджет
  > не делится нацело, и на них проверка ничего не говорит. Официальная формулировка
  > Ozon про включительность границы отсутствует.
- **Связь со `state`** (совпадение полное, 119 из 119): у `FINISHED` и `ARCHIVED` дата
  `to_date` в прошлом; у `RUNNING` и `INACTIVE` — в будущем. `INACTIVE` при `to_date` в
  будущем означает заведённую, но ещё не стартовавшую кампанию.

### 1.4. Ловушки реализации

**Не прогонять эти даты через конвертер `DD.MM.YYYY`.** Базовое ТЗ §3.6 требует конвертера
для дат **внутри CSV-отчётов** — там формат действительно `DD.MM.YYYY`. Поля `fromDate` и
`toDate` приходят из **JSON** и уже в `YYYY-MM-DD`. Пропускать их через тот же конвертер
нельзя — он их испортит.

**Не путать с параметрами запроса статистики.** В теле `POST /api/client/statistics`
используются `dateFrom` и `dateTo` — это **период отчёта**, задаваемый нами. `fromDate` и
`toDate` — **период кампании**, возвращаемый Ozon. Четыре разных имени, две разные сущности.

**Отсутствие поля в объекте кампании обрабатывать как `null`**, а не как пустую строку и не
падением. На замере пустых значений не было (119 из 119 заполнены во всех трёх полях), но
гарантии API на это нет.

**Регистр ключей API.** Ключи читать точно: `state`, `fromDate`, `toDate` — именно в таком
написании. В том же ответе есть поля с заглавной буквы (`PaymentType`, `ProductAdvPlacements`),
то есть Ozon в этом ответе непоследователен, и обращение к ключу без учёта регистра вернёт
пусто.

### 1.6. Критерии приёмки (дополняют §9)

- [ ] `get_campaign_dict` возвращает **13 колонок** в порядке из §1.2.
- [ ] `state`, `from_date`, `to_date` заполнены из ответа `GET /api/client/campaign`;
      число HTTP-запросов не выросло.
- [ ] `from_date` и `to_date` соответствуют маске `YYYY-MM-DD` и **совпадают со значением
      API посимвольно** (никакого переформатирования).
- [ ] Кампания со значением `state`, которого нет в таблице §1.3, проходит через функцию

      Проверяется подстановкой вымышленного значения в тестовый ответ.
- [ ] Отсутствие любого из трёх ключей в объекте кампании даёт `null` в колонке,
      а не исключение и не пустую строку.
- [ ] Ни одно из трёх полей не проходит через конвертер дат `DD.MM.YYYY`.

### 1.7. Решение заказчика по именам колонок — ПОДТВЕРЖДЕНО

**Имена колонок — `from_date` / `to_date` (snake_case).** Подтверждено заказчиком
17.09.2026. Вариант с сохранением имён API (`fromDate` / `toDate`) рассмотрен и отклонён.

Основание: весь выход базового ТЗ именован в snake_case (`campaign_id`, `campaign_name`,
`source_type_id`, `id_key_camp`), camelCase из API наружу нигде не протекает. Колонка
`state` в обоих вариантах называлась бы одинаково.

**Для разработчика это означает:** ключи в JSON-ответе API остаются `fromDate` / `toDate`
(их читаем как есть, см. §1.4 про регистр), а в выходную таблицу они кладутся под именами
`from_date` / `to_date`. Переименование — только на выходе.

## К-2. Статистика кампаний: учитывать строку «Корректировка», добавить поле `costs_corr`

**Заменяет:** §4.2 (`get_campaigns_daily_stat`), §7.2 (пример таблицы), правило про строку
«Корректировка» в §3.6, дополняет §9 (критерии приёмки).

### 2.1. Суть проблемы

Базовое ТЗ §3.6 предписывает: «**Строка `Корректировка`:** корректировка бюджета без даты —
пропускать». Указание выполняется буквально, и из-за него **расход считается неверно**.

Строка «Корректировка» несёт сумму, на которую Ozon правит дневной расход кампании
(чаще всего — срезка при выходе за дневной бюджет). Ozon **включает** её в свой итог
«Всего», а реализация её отбрасывает. Итог: `costs_nds` систематически **завышен**.

Замер на живых данных за 2026-09-10 (8 кампаний, чей период накрывает этот день):

| | сумма по объявлениям | корректировка | итог «Всего» от Ozon |
|---|---:|---:|---:|
| 7 кампаний с данными | 188 205.86 | −587.36 | **187 618.50** |

Строка «Корректировка» нашлась у **7 из 7** кампаний с данными — это норма для аккаунта,
а не редкий случай. Смещение **одностороннее**: корректировки отрицательные, значит расход
всегда завышается и никогда не занижается, а ошибка накапливается по дням.

Наглядный пример: у кампаний `40391217` и `40391585` после учёта корректировки расход
становится ровно **27 200.00** — это дневной лимит бюджета. Без корректировки в таблицу
попадали 27 331.49 и 27 276.16 — числа, которых у Ozon нет нигде.

### 2.2. Что меняется

**Строку «Корректировка» больше не игнорировать.** Её сумма забирается в новое поле и
учитывается в расходе кампании за этот день.

**Новое поле `costs_corr`** — величина корректировки по кампании за день, **по модулю**
(всегда неотрицательна). Тип — число, как и остальные денежные поля.

**Порядок колонок** — было 12, стало 13; `costs_corr` встаёт **сразу после `costs_nds`**:

```
date, campaign_id, impressions, clicks, costs_nds, costs_corr,
costs_without_nds, ak, costs_nds_ak, costs_without_nds_ak,
account_id, source_type_id, id_key_camp
```

### 2.3. Расчёт — знак имеет значение

🔴 **В колонку `costs_corr` пишется МОДУЛЬ, а в расчёт `costs_nds` корректировка входит
СО СВОИМ ЗНАКОМ, как её прислал Ozon.** Это два разных значения одной величины, и путать
их нельзя.

```
сумма_по_объявлениям = сумма «Расход, ₽, с НДС» по строкам объявлений за день
корректировка        = сумма строк «Корректировка» за день, СО ЗНАКОМ (обычно отрицательна)

costs_nds  = сумма_по_объявлениям + корректировка        // знак учитывается
costs_corr = abs(корректировка)                          // модуль, в таблицу
```

Далее производные считаются **от скорректированного `costs_nds`** — их формулы из базового
ТЗ не меняются, но вход у них теперь другой:

```
costs_without_nds    = costs_nds / 1.22
ak                   = 0.5
costs_nds_ak         = costs_nds * 1.5
costs_without_nds_ak = costs_without_nds * 1.5
```

**Корректировки нет в отчёте** → `costs_corr = 0.0`, `costs_nds` не меняется.

**Округление не применяется** — денежные поля пишутся как есть, без приведения к 2 знакам
(решение заказчика; поведение совпадает с базовым ТЗ, где округление предусмотрено только
в `get_admin_audit`).

### 2.4. Ловушки реализации

**Строк «Корректировка» может быть больше одной** — суммировать все, а не брать первую.

**Не путать с «Всего».** У обеих строк пустое поле `День` в привычном смысле: там текст,
а не дата. `Всего` по-прежнему **пропускается** — это итог, его сложение с объявлениями
удвоило бы расход. `Корректировка` теперь **учитывается**. Различать строго по значению
первой колонки.

**Не искать в строке ничего, кроме суммы.** Замер: в строке «Корректировка» заполнены
**только** `День` и колонка расхода, все остальные поля пустые:

```
Корректировка;;;;;;;;;-119,24
```

**Гард на знак.** Все наблюдавшиеся корректировки отрицательные. Если придёт
**положительная**, модуль в `costs_corr` сделает её неотличимой от срезки, при том что
`costs_nds` вырастет. Реализация обязана в этом случае **написать предупреждение в лог**
с перечнем кампаний, а не молча записать модуль.

### 2.5. Область действия — только эта таблица

🔴 **Сама К-2 описывает только `get_campaigns_daily_stat`.** У строки «Корректировка»
**поле `ID баннера` пусто**, поэтому на уровне объявлений её нельзя отнести к конкретной
строке напрямую — там нужно правило распределения. Оно получено от заказчика и вынесено
в отдельные корректировки.

**Кто закрывает уровень объявлений:**

| Таблица | Чем закрыта | Состояние |
|---|---|---|
| `get_campaigns_daily_stat` | **К-2** (этот раздел) | закрыта |
| `get_ads_daily_stat` | **К-3** — распределение пропорционально показам | закрыта |
| `get_video_ads_daily_stat` | **К-4** — то же правило | закрыта |
| `get_reach_ads_daily_stat` | — | **неприменимо**: денежных полей нет |
| `get_reach_campaigns_daily_stat` | — | **неприменимо**: денежных полей нет |
| `get_admin_audit` | **К-5** | закрыта, см. ниже |

## К-3. Статистика объявлений: распределять корректировку пропорционально показам

**Заменяет:** §4.3 (`get_ads_daily_stat`), §7.3 (пример таблицы), дополняет §9.
**Зависит от:** К-2 (там описана сама строка «Корректировка» и её влияние на расход).

### 3.1. Суть изменения

Строка «Корректировка» относится ко **всей кампании**: поле `ID баннера` в ней пусто
(см. К-2 §2.4), поэтому базовая реализация её отбрасывает и расход по каждому объявлению
оказывается завышен.

**Правило заказчика (17.09.2026):** корректировка кампании распределяется между её
объявлениями **пропорционально показам** этих объявлений за тот же день.

Как и в К-2, добавляется поле **`costs_corr`** — доля корректировки, пришедшаяся на это
объявление, **по модулю**.

### 3.2. Расчёт

```
сумма_показов_кампании = сумма «Показы» по строкам объявлений кампании за день
доля_объявления        = показы_объявления / сумма_показов_кампании
часть                  = корректировка_кампании (СО ЗНАКОМ) * доля_объявления

costs_nds  = расход_объявления + часть      // знак учитывается
costs_corr = abs(часть)                     // модуль, в таблицу
```

Производные считаются **от скорректированного `costs_nds`**, формулы из базового ТЗ
не меняются:

```
costs_without_nds = costs_nds / 1.22     ak = 0.5
costs_nds_ak = costs_nds * 1.5           costs_without_nds_ak = costs_without_nds * 1.5
```

🔴 **Округления нет** (решение заказчика). Это не косметика: без округления сумма частей
**точно** равна целому, и инвариант §3.6 выполняется без остатка. Если округление до копеек
будет введено позже — появится расхождение в 1–2 копейки и потребуется отдельное правило,
кому отдавать остаток.

### 3.3. Граничный случай: нулевые показы

**Сумма показов по кампании = 0, а корректировка есть** → делить не на что. Правило
заказчика: **распределить поровну** между объявлениями кампании и **написать предупреждение
в лог** с номером кампании.

```
часть = корректировка_кампании / количество_объявлений_кампании
```

Молча пропускать этот случай нельзя: корректировка исчезнет, и сумма по объявлениям
разойдётся с итогом кампании.

> На данных за 2026-09-10 случай не встретился ни разу: единственная кампания с нулевыми
> показами (`37217412`) имеет и нулевую корректировку. То есть ветка по живым данным
> **не проверена** — её обязательно закрыть тестом на искусственном CSV.

### 3.4. Ловушки реализации

**Долю считать по СТРОКЕ отчёта, а не по объявлению.** Ozon отдаёт строку на каждую
**платформу показа**, поэтому строк на объявление за день может быть несколько.

> **Обновление 21.09.2026:** это уже не гипотеза. Замер за 12.09.2026 нашёл два таких
> объявления, и платформа решением владельца внесена в зерно обеих таблиц уровня
> объявлений — см. **К-7**, который заменяет этот абзац в части зерна. Правило
> «доля по строке» остаётся в силе и становится буквальным: строка = объявление × платформа.

**Распределять в пределах ОДНОЙ кампании и ОДНОГО дня.** Корректировка кампании A не может
попасть на объявление кампании B; корректировка за 10.09 — на показы 11.09.

**Знак — как в К-2.** В `costs_corr` идёт модуль, в `costs_nds` часть входит со своим
знаком. Положительная корректировка требует предупреждения в лог (К-2 §2.4).

**Объявление с нулевыми показами внутри кампании, где показы есть**, получает долю 0 —
то есть его расход не корректируется. Это следствие выбранной базы распределения (показы),
а не ошибка.

### 3.5. Область действия

К-3 распространяется **только на `get_ads_daily_stat`**.

- `get_video_ads_daily_stat` — тоже уровень объявлений и тоже с расходом, но решение по
  нему заказчиком **отложено** (17.09.2026). Его расход остаётся завышенным — известное
  расхождение.
- `get_reach_ads_daily_stat` — правило неприменимо: денежных полей в таблице нет.
- `get_campaigns_daily_stat` — закрыт К-2, распределение там не нужно.

### 3.6. Критерии приёмки (дополняют §9)

      Итоговое число колонок — **17**, с учётом `platform` из К-7 (К-3 сам по себе
      давал 16; К-7 добавляет ещё одну колонку к этой же таблице).
- [ ] 🔴 **По каждой кампании сумма `costs_nds` по её объявлениям равна строке «Всего»

## К-4. Видео-статистика: то же распределение корректировки, что и в К-3

### 4.5. 🔴 ОТКРЫТОЕ РЕШЕНИЕ ЗАКАЗЧИКА: НДС у видео вычитается дважды

Это **отдельный дефект**, не связанный с корректировкой, и К-4 его **намеренно
НЕ исправляет** — нужно решение заказчика, потому что меняется смысл денежной колонки.

**Что происходит.** У баннеров источник — «Расход, ₽, **с НДС**», у видео —
«Расход, ₽», то есть сумма **БЕЗ НДС**. Обе кладутся в поле с одним именем
`costs_nds`. Далее для обеих считается `costs_without_nds = costs_nds / 1.22` —
и у видео НДС вычитается из суммы, где его не было.

**Два следствия:**
1. `costs_without_nds` у видео занижен примерно на 18 %.
2. `costs_nds` из видео-таблицы **нельзя складывать** с `costs_nds` баннерных
   таблиц — это величины с разным смыслом под одним именем.

**Варианты решения (выбор за заказчиком):**

| | что делать | последствия |
|---|---|---|
| **А** | `costs_nds = «Расход, ₽» * 1.22`, `costs_without_nds` = как есть | обе таблицы становятся сопоставимы; требует уверенности, что ставка 22 % применима к видео |
| **Б** | у видео переименовать колонку в `costs_without_nds`, а `costs_nds` не заполнять | честно отражает источник; ломает единообразие состава колонок |
| **В** | оставить как есть, задокументировать | ничего не ломается, дефект остаётся; суммировать таблицы по-прежнему нельзя |

До решения реализуется **вариант В** — поведение базового ТЗ сохранено.

## К-5. Сводный аудит: поле `costs_corr` и защита join

**Заменяет:** §4.7 (`get_admin_audit`), §7.7, дополняет §9.
**Зависит от:** К-2 (агрегат строится поверх `get_campaigns_daily_stat`).

### 5.1. Что меняется

Состав колонок: было 9, стало **10** — `costs_corr` сразу после `costs_nds`, как во всех
остальных денежных таблицах. Значение — **сумма** корректировок по ключу группировки.

Правка К-2 **наследуется автоматически**: собственного парсинга CSV у агрегата нет, он
суммирует уже скорректированную статистику кампаний. Отдельного правила распределения
здесь не нужно.

Ключ группировки не меняется: `date × account_id × source_type_id × owner_id`.
Суммируются `impressions`, `clicks`, `costs_nds`, **`costs_corr`**, `costs_without_nds`.

### 5.2. Округление — единственное исключение в проекте

🔴 В `admin_audit` округление денег до 2 знаков **сохраняется** (оно есть в базовом ТЗ
по дизайну). Во всех остальных таблицах К-2…К-4 округления нет. Это расхождение
**намеренное**: агрегат — витринная таблица, а не источник для дальнейших расчётов.
`costs_corr` округляется так же, как соседние денежные поля.

### 5.3. Защита join по `campaign_id`

🔴 `owner_id` берётся из справочника join-ом по `campaign_id`. **Обе стороны join обязаны
иметь строковый тип ключа.** При разнотипных ключах поведение зависит от версии
библиотеки: pandas 3 падает с ошибкой, более старые версии молча не находят совпадений —
и тогда `owner_id` пуст, строки уходят из группировки, а суммы оказываются неполными
без единой ошибки. Связано с находкой К-1 (`id` приходит строкой, но код донора
это не гарантирует).

**Постусловие:** после join число строк с пустым `owner_id` обязано быть **0**.
Ненулевое — отказ, а не предупреждение: суммы уже неверны.

### 5.4. Гард на формат даты во входной таблице

🔴 Перед агрегацией проверять, что `date` в источнике соответствует `YYYY-MM-DD`.

**Зачем.** Файл промежуточной таблицы, открытый и сохранённый в Excel с русской локалью,
молча меняет ISO-дату на `ДД.ММ.ГГГГ`. Числа при этом не страдают, файл парсится, суммы
верны — но дата входит в ключ зерна, и порча уезжает в витрину. Случай наблюдался при
разработке 17.09.2026: агрегат собрался зелёным и записал `10.09.2026` в выход.

Проверка стоит одного сравнения и обязана быть **отказом** с внятным сообщением.

### 5.5. Критерии приёмки (дополняют §9)

- [ ] `get_admin_audit` возвращает **10 колонок**: базовые + `costs_corr` после `costs_nds`.
- [ ] Зерно `date × account_id × source_type_id × owner_id` уникально.
- [ ] 🔴 **Закон сохранения:** суммы `impressions`, `clicks`, `costs_nds`, `costs_corr`,
      `costs_without_nds` по всему агрегату равны суммам по входной таблице кампаний
      (допуск 0.01 на строку группы — из-за округления).
- [ ] Строк с пустым `owner_id` после join — **0**.
- [ ] Источник с датой не в формате `YYYY-MM-DD` вызывает **отказ**, а не тихую обработку.
- [ ] `costs_corr` неотрицательно.

большинство из них в конкретный день не работали, и запросы уходят впустую.

Замер 2026-09-10: в аккаунте **119** кампаний, данные за этот день есть у **6**.
Полная выгрузка — 12 батчей, 36 HTTP-вызовов, из них три упёрлись в `429 Too Many
Requests`. Отбор по правилу ниже — **8 кампаний, 1 батч, 3 вызова, ни одного 429**,
и **ни одна строка с данными не потеряна**.

При суточном лимите в 1000 скачиваний отчётов это разница между «месяц влезает
впритык» и «влезает с запасом».

### 6.2. Правило — предикат зависит от типа отчёта

🔴 **Предикатов ДВА, и подменять один другим нельзя.**

**А. Дневные таблицы** — `get_campaigns_daily_stat`, `get_ads_daily_stat`,
`get_video_ads_daily_stat`. Запрос идёт за один день (`dateFrom == dateTo`), поэтому:

```
from_date <= день_запроса <= to_date
```

**Б. Охватные таблицы** — `get_reach_campaigns_daily_stat`, `get_reach_ads_daily_stat`.
Запрос идёт за **интервал** `[global_start_date .. D]`, поэтому кампания нужна, если её
период **пересекает** окно накопления:

```
from_date <= date_to   И   to_date >= global_start_date
```

> **Почему нельзя применить предикат А к охвату.** Кампания, закончившаяся в середине
> окна, всё равно дала охват внутри него, и её обязательно надо запросить. Замер:
> для окна `[2026-08-01 .. 2026-09-12]` предикат А отобрал бы 8 кампаний вместо 25 —
> **потеря 17 из 25**. На узком окне `[2026-09-10 .. 2026-09-12]` оба предиката дают
> одинаковые 8, то есть ошибка на коротких периодах **не проявляется** и вылезет позже.

**Дополнительный фильтр для видео.** У `get_video_ads_daily_stat` поверх предиката А
действует `advObjectType == "VIDEO_BANNER"` (это есть и в базовом ТЗ).

**`get_admin_audit`** собственных запросов не делает — правило приходит к нему через
`get_campaigns_daily_stat`.

### 6.3. Почему НЕ по статусу кампании

Отбор по `state ∈ {RUNNING, INACTIVE}` выглядит естественным и **работает только для
свежих дат**. Статус отражает состояние кампании **сейчас**, а статистику мы просим за
**прошлое**.

Замер: за 2026-09-16 (почти сегодняшний день) отбор по статусу не терял ничего — 8 из 8.
За 2026-09-10 он потерял **3 кампании из 8**: они в тот день работали, но к моменту
запроса уже перешли в `FINISHED`. Потеря **молчаливая** — отказов нет, файлы приходят,
просто кампаний меньше.

Правило по периоду от момента запроса не зависит и верно для любой даты в прошлом.

### 6.4. Кампании без дат

Кампания с пустым `from_date` или `to_date` под правило **не подпадает** — сравнивать
не с чем. Такие кампании **не отбрасывать молча**: вести отдельный счётчик и печатать
его в отчёте о выгрузке.

Замер 17.09.2026: таких кампаний **0 из 119**, то есть ветка по живым данным не
проверена. Гарантии, что API всегда заполняет обе даты, нет.

### 6.5. Что это НЕ меняет

Размер батча (**10** кампаний на запрос), ограничение на одновременные задачи (**3**),
пауза между submit, обработка `429` — всё по базовому ТЗ §3.4 и §5 без изменений.
Правило меняет только **состав** кампаний, а не механику запросов.

### 6.6. Критерии приёмки (дополняют §9)

- [ ] Дневные таблицы отбирают кампании по предикату А, охватные — по предикату Б.
- [ ] 🔴 **Сравнительный прогон:** выгрузка с отбором и без него за один и тот же день
      дают **одинаковый набор строк с данными**. Правило обязано экономить запросы,
      не теряя данных.
- [ ] Число HTTP-запросов при отборе меньше, чем без него, — зафиксировать в отчёте.
- [ ] Кампании с пустыми датами попадают в отдельный счётчик, он печатается.
- [ ] Для видео фильтр по `advObjectType` применяется **дополнительно** к предикату А.

## К-7. Платформа — часть зерна таблиц уровня объявлений

**Заменяет:** зерно и состав колонок в §4.3 (`get_ads_daily_stat`) и §4.5
(`get_reach_ads_daily_stat`), а также правило суммирования по платформам в §4.5.
**Решение владельца:** 21.09.2026, вариант «платформа в зерне».

### 7.1. Суть изменения

Ozon отдаёт **строку на каждую платформу показа**. Базовая реализация этот факт не
учитывает: `get_ads_daily_stat` строки не схлопывает (и потому **нарушает собственное
зерно**), а `get_reach_ads_daily_stat` суммирует по платформам, теряя разрез.

Обе таблицы уровня объявлений получают колонку **`platform`** — сразу после `ad_name`,
и зерно становится:

```
date x campaign_id x ad_id x platform
```

| таблица | было колонок | стало |
|---|---:|---:|
| `get_ads_daily_stat` | 16 (К-3) | **17** |
| `get_reach_ads_daily_stat` | 10 | **11** |

Значение берётся из колонки CSV **«Платформа»**. Пустое значение записывать как
`не указана`, а не пустой строкой — иначе такие строки выпадут из группировок.

Кампанийные таблицы (`get_campaigns_daily_stat`, `get_reach_campaigns_daily_stat`)
изменения **не касаются**: там зерно на уровне кампании.

🔴 **`get_video_ads_daily_stat` тоже НЕ затрагивается — и это не решение, а свойство
данных.** В видео-отчёте колонки «Платформа» **нет вовсе**: замер по реальному заголовку
даёт 23 колонки, платформы среди них ни одной (в баннерном отчёте — 10 колонок, платформа
есть). Брать её там неоткуда, поэтому зерно видео-таблицы остаётся
`date × campaign_id × ad_id`, 22 колонки по К-4.

> **Следствие для приёмника:** таблицы `get_ads_daily_stat` и `get_video_ads_daily_stat`
> имеют РАЗНОЕ зерно и напрямую не объединяются. При сведении их в одну витрину
> видео-строкам нужно проставлять платформу-заглушку (`не указана`) либо сводить
> баннерную таблицу до уровня объявления.

### 7.2. 🔴 Группировка при расчёте `increment` обязана совпадать с зерном

Для `get_reach_ads_daily_stat` это **самый опасный пункт всей корректировки**.

`increment` считается как `reach.diff()` **внутри группы**. Пока зерном было
`(кампания, объявление)`, группой было то же самое. С платформой в зерне группа обязана
стать:

```
(campaign_id, ad_id, platform)
```

**Что происходит, если платформу в группе забыть.** После сортировки соседями в группе
оказываются строки разных платформ, и разность берётся между ними. Замер 21.09.2026,
объявление `703367`:

| date | platform | reach | increment ПРАВИЛЬНО | increment БЕЗ платформы в группе |
|---|---|---:|---:|---:|
| 2026-09-10 | Мобильное приложение | 123 476 | 123 476 | 123 476 |
| 2026-09-11 | Мобильное приложение | 243 830 | 120 354 | 120 354 |
| 2026-09-12 | Десктоп | 1 | **1** | **−243 829** |
| 2026-09-12 | Мобильное приложение | 358 334 | **114 504** | **358 333** |

Ошибка не только в знаке: прирост мобильного приложения завышается втрое.

**Требование к реализации:** группа задаётся **одной константой**, и та же константа
используется для зерна, для `diff` и для проверки монотонности. Три независимых списка
полей разъедутся при первой же правке.

### 7.3. Следствия, принятые владельцем

🔴 **`id_key_ad` перестаёт быть уникальным — это ПРИНЯТО (владелец, 21.09.2026).**
У платформенных строк одного объявления ключ одинаков:

```
2026-09-12  40391217  715132  Мобильное приложение   id_key_ad = 1_40391217_715132
2026-09-12  40391217  715132  Десктоп                id_key_ad = 1_40391217_715132
```

Формула ключа **не меняется**: `id_key_camp + "_" + ad_id`, платформа в него **не входит**.
Ключ остаётся идентификатором объявления, а не строки таблицы.

> **Что это значит для приёмника данных.** `id_key_ad` **нельзя** использовать как
> первичный ключ строки и нельзя соединять по нему «один к одному» — соединение даст
> размножение строк. Первичный ключ строки — полное зерно из §7.1. Проверку
> уникальности `id_key_ad`, если она где-то стоит, **снять**: она будет давать ложную
> тревогу на штатных данных.

**Корректировка распределяется по СТРОКЕ** (объявление × платформа) пропорционально
показам — правило К-3 §3.2 без изменений, просто строк стало больше. Десктопная строка
с одним показом получает свою долю: замер 12.09 — `costs_corr = 0.0001 ₽`.

### 7.4. Семантика: reach по платформам НЕ складывается

`reach` — дедуплицированная метрика. Один человек, увидевший объявление и в приложении,
и на десктопе, при суммировании строк будет посчитан **дважды**.

Прежнее поведение (сумма по платформам) этим дефектом обладало. **Разбивка по платформам
от него свободна**: каждая строка несёт охват своей платформы и ничего не складывается.
Это довод в пользу К-7 сверх сохранения разреза.

Соответственно, сумма `reach` по строкам объявления **не равна** его дедуплицированному
охвату и может быть только больше либо равна.

### 7.5. Масштаб на живых данных

Замер 10–12.09.2026, 7 кампаний:

| платформа | строк | показы | охват |
|---|---:|---:|---:|
| Мобильное приложение | 39 | 2 921 602 | 5 004 735 |
| Десктоп | 2 | 2 | 2 |

Объявлений с несколькими платформами за день — **2 из 39**. Сегодня десктоп
статистически пренебрежим, но это наблюдение одного периода: без разреза рост
десктопного трафика остался бы невидимым, а охват объявления начал бы завышаться.

### 7.6. Критерии приёмки (дополняют §9)

- [ ] Обе таблицы уровня объявлений содержат `platform` сразу после `ad_name`:
      `get_ads_daily_stat` — 17 колонок, `get_reach_ads_daily_stat` — 11.
- [ ] Зерно `date × campaign_id × ad_id × platform` уникально в обеих.
- [ ] 🔴 **`increment` считается по группе `(campaign_id, ad_id, platform)`**, и это
      подтверждено проверкой: отрицательных `increment` — **0**. Тест на объявлении
      с двумя платформами обязателен: при группе без платформы он должен краснеть.
- [ ] `reach` не убывает по времени **внутри группы с платформой**.
- [ ] Суммы по паре кампания-день по-прежнему совпадают со строкой «Всего» от Ozon.
- [ ] 🔴 **Проверка уникальности `id_key_ad` снята** — её нарушение штатно (§7.3).
- [ ] Пустая «Платформа» даёт значение `не указана`, строка не теряется.
- [ ] Свёртка таблицы по платформам воспроизводит прежний вариант — разовая сверка
      при внедрении, чтобы доказать, что разрез ничего не добавил и не потерял.

## Приложение А. Расхождения базового ТЗ с фактическим поведением API

Не входят в объём К-1 — вынесены отдельно, потому что обнаружены при подготовке этой
корректировки и влияют на реализацию. Решение по ним за заказчиком.

**А.1. Кодировка CSV-отчётов — UTF-8 BOM, а не cp1251.**
Базовое ТЗ §3.6 предписывает `mb_convert_encoding($csv, 'UTF-8', 'CP1251')`. Замер по всему
кэшу отчётов проекта 02_01: у **352 файлов из 352** первые байты `EF BB BF` (BOM UTF-8), все
352 корректно декодируются как UTF-8, ни одного файла в cp1251. Конвертация из cp1251,
применённая к UTF-8, даст испорченный текст. Затрагивает все функции статистики, не только
справочник.

**А.2. Поле `id` приходит строкой, а не integer.**
Базовое ТЗ §3.6 и §4.1 утверждают, что `id` в JSON — integer. Замер живого ответа:
`"id": "42163009"` — строка, у всех 119 кампаний. Само требование ТЗ («хранить
`campaign_id` как строку») остаётся верным, неверно обоснование — приведение типа
фактически ничего не меняет.
